## D. Capability reality, and the control that proves the rule is not a blanket refusal

```text
every capability on every shipped profile   UNKNOWN
deepseek/deepseek-flash · mimo/mimo-v2.6-flash · mimo/mimo-v2.6-pro
five capabilities each, fifteen slots, none verified
no provider call has ever been made in this repository
```

```text
request requires a capability  +  all candidates UNKNOWN  ->  NO_ELIGIBLE_MODEL
```

That is the v1 design. Reading `UNKNOWN` as "probably fine" would make the Router
select on claims nobody tested.

**T9 is the control.** A synthetic `ModelProfile` whose `tool_calling` is
`VERIFIED` produces `SELECTED`. It is constructed in memory, is **never
registered**, and no provider is called to produce it — §14 forbids the Router
from probing and §6.2 forbids it from promoting a status, so the control cannot
be earned. Without T9, T7 and T8 pass vacuously.

AI-02 refused the first version of that control: its `CapabilityEntry` rules
require a `VERIFIED` entry to carry a dated observation and an evidence
reference, and its profile-level rule requires provenance to match. The control
was corrected to satisfy AI-02 rather than to be exempted from it.

## G2. Round-one review findings -- four, all fixed here

Recorded in the order they were found rather than folded into the sections above,
so the sequence is traceable and the earlier numbers stay visible as superseded.

```text
P1  provider enablement fail-open
    FOUND   `enabled_providers=None` meant "do not check", so a provider AI-02
            ships `enabled: false` could be SELECTED by simply not passing a
            config. AI-02's ProviderConfig is fail-closed; this was the one
            fail-open path in the module.
    FIXED   absent enablement now means NO provider is enabled. The `is not None`
            guard is gone, because that guard was the defect.
    REGRESSION  omitting it selects nothing; an empty set selects nothing; a
            disabled provider is not selected; the positive control still selects
            when its provider IS enabled.
    REVERIFIED  134 routing tests, 2271 whole repository.

P1  INVALID_RULES was frozen and unreachable
    FOUND   RoutingOutcome.INVALID_RULES exists and section 12.4 requires it, but
            the only path to an invalid rule set was a raised InvalidRules
            escaping the Router boundary. An exception is not a RoutingOutcome,
            so the frozen member could never be produced.
    FIXED   evaluate_mapping now takes the rule set as a raw mapping and projects
            InvalidRules to INVALID_RULES, with no selection and no partial
            application: validation completes before any rule runs.
            RuleSet.from_mapping remains the validator and still raises.
    REGRESSION  five invalid shapes, a duplicate rule_id, and a mixed
            valid/invalid set all produce INVALID_RULES with selected None. The
            valid control still selects.
    REVERIFIED  as above.

P2  the Guard import boundary was stated and not checked
    FOUND   ROUTING_FORBIDDEN_IMPORTS listed `plugins.guard` beside top-level
            roots, and the check compared top-level roots only, so the entry
            could never match. routing/request.py legitimately imports
            plugins.guard.vocabulary for ActorType and PermissionLevel -- a
            frozen-vocabulary import, not a Guard implementation dependency, and
            the boundary could not tell the two apart.
    FIXED   the check now inspects the FULL module path against an allowlist of
            exactly plugins.guard.vocabulary. Every other plugins.* module fires,
            from both `import x` and `from x import y`.
    REGRESSION  mutation-tested: plugins.guard.decision, plugins.evidence.foo and
            plugins.security_tools.adapter each make Layer 0 FAIL, and
            plugins.guard.vocabulary stays silent.
    REVERIFIED  Layer 0 PASS (16 checks).

P2  the request schema was permissive
    FOUND   Section 5.1 declares candidates: [{model_ref: string}], and the
            parser accepted a bare "provider/model" string. It also accepted any
            string as requested_capability, so an unknown capability became a
            routing miss (NO_ELIGIBLE_MODEL) instead of INVALID_REQUEST.
    FIXED   a bare candidate string is refused, as is a candidate carrying an
            undeclared field, and requested_capability is validated against
            AI-02's CapabilityName. RuleSet validates the same vocabulary in
            match.requested_capability. No Router-side capability vocabulary was
            created.
    REGRESSION  bare string, unknown field, five real capabilities accepted, an
            unknown capability refused as INVALID_REQUEST and specifically not as
            NO_ELIGIBLE_MODEL, and a rule matching an unknown capability is
            INVALID_RULES.
    REVERIFIED  as above.
```

## G. Two defects found and fixed in this PR

**The AI-02 transport-confinement guard was tripped again.** `TestLiveOnlyTransport`
scans `tests/` for the live-only transport's name, and a test that *forbids* it by
naming it still names it. This is the same class of mistake AI-06 recorded. The
check is now structural — it asserts no `routing/` module imports a leaf module
whose name contains `transport` or `http` — rather than a name list.

**AI-07-A's absence assertions were superseded, not broken.**
`tests/unit/test_ai07_contract_consistency.py` asserted `routing/` contained no
Python, which was the honest claim for a contract-freeze phase. AI-07-B implements
the router, so the class now asserts the properties that survive: `routing/` is
still not a plugin package, the Router exists where the core service belongs, and
no invented profile was created to match the roadmap's sketch.
